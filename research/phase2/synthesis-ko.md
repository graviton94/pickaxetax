# 2단계 종합: 입력을 키우는 것은 무엇이고, 어떤 지렛대가 그것을 움직이나

상태: **초안 v2, 2026-10-06.** 영어 원문 `synthesis.md`의 한국어판이고, 근거는 `log.md`의 각 사이클입니다.
한 사람의 Claude Code 세션 10개(판 2, 입력 68.4억 토큰)를 쟀습니다. 이 문서는 낭비 판정이 아닙니다.
낭비는 코드북으로만 정하고, 사람 판정이 필요한 갈래는 블라인드 판정을 기다립니다.

## 1. 하나의 원리

API 호출은 매번 맥락 전체를 처음부터 다시 처리합니다. 그래서 세션의 입력은 호출마다의 맥락을 더한 값입니다.

> **입력 = 호출마다 맥락의 합 = (걸음 수) × (평균 맥락)**

2단계에서 잰 것은 모두 이 두 인수 중 하나에 대한 이야기입니다.

- **걸음.** 지시 하나의 입력 편차 중 87%를 호출 수가 설명합니다(사이클 B).
  - 비싼 지시는 재시도 고리가 아닙니다. 읽고, 돌리고, 고치는 평범한 걸음이 길게 이어진 지시입니다(중앙값 75걸음, 보통 지시는 11걸음).
  - 재시도와 폴링 고리는 모두 합쳐 입력의 약 2%입니다(B2).
- **맥락.** 압축이 상한(약 78.3만 토큰)에서만 일어나므로 맥락은 늘 상한 근처에 있습니다.
  - 세 번째 지시 뒤의 호출은 약 42만 토큰을 싣고, 그중 약 80%는 이미 끝난 지시에서 넘어온 내용입니다(B).
  - 보이는 것 중 가장 큰 덩어리는 AI가 직접 쓴 내용(파일 본문, 스크립트, 편집)입니다. 입력의 22.9%이고, 다시 읽히는 경우는 15% 정도입니다(A2).
  - 맥락 증가의 약 30%는 기록에 보이지 않습니다. 대부분 모델의 생각 과정, 호출마다 붙는 고정 부분, 이미지입니다(C2).

**상한이 평균을 정합니다.** 긴 세션의 맥락은 6.4만과 78.3만 사이를 톱니처럼 오갑니다.
- 넣는 양을 줄이는 정책(잘라내기, 포인터)은 다음 압축을 늦출 뿐 평균은 거의 그대로입니다(B3: 포인터만으로 −4%).
- 평균을 낮추는 것은 경계를 옮기는 일입니다. 새 세션을 시작하거나 더 일찍 압축하는 것입니다.
- 최적 상한에는 닫힌 식이 있습니다: **C\* = P + √(2g(P + R))**. 재고 관리의 경제적 주문량과 같은 꼴입니다. 여기서는 약 8만~9만 토큰(비용 가중 11만~16만)이고, 오늘은 78.3만입니다(B4, E6).

## 2. 돈과 시간으로

**돈**(목록가 비율, 출력은 입력의 5배; C5):
- 지출의 71~74%가 캐시 읽기, 16%가 1시간 캐시 쓰기, 추정 9~12%가 출력입니다.
- **지출의 약 절반(52~54%)이 이미 끝난 지시에서 넘어온 맥락을 다시 읽는 데 쓰였습니다.** 캐시가 만료된 뒤 다시 쓴 값까지 더하면 62~64%입니다.
- 1시간 캐시는 이 사람의 작업 리듬에 맞는 선택이었습니다. 전부 5분 캐시였다면 17% 더 들었습니다(C7).
- 이 숫자들은 고정된 가격 비율(캐시 읽기 0.1, 쓰기 1.25/2.0, 출력 5)에 기댑니다. 비율을 48가지로 바꿔 봐도 지렛대의 순서와 1시간 캐시라는 결론은 바뀌지 않았습니다(C8).
- "지출의 절반"은 캐시 읽기 값이 입력의 약 0.06~0.09배 이상일 때만 성립합니다. 다시 쓴 값까지 더하면 어떤 설정에서도 56~69%입니다.
- 가장 많이 움직이는 것은 기계적 하한의 비용 몫입니다(4.7~15.4%).

**시간**(C6):
- 맥락이 커지면 응답이 느려지지만, 그 폭은 작습니다. 10만 토큰당 0.2~0.4초이고, 모델 시간 61시간 중 6~11%입니다.
- 압축 한 번은 약 130초 걸립니다.
- 그래서 지렛대는 토큰과 돈을 아껴 주지만 시간은 거의 아껴 주지 않습니다. 재시작만 예외입니다.

## 3. 지렛대를 한 저울에

| 지렛대 | 덜 처리했을 입력 | 가정 | 누가 당길 수 있나 |
|---|---:|---|---|
| 필요할 때만 다시 불러오기 (오라클) | 41.5% (탐지 기준에 따라 35~56%) | 미래를 앎 | — (상한) |
| 다시는 안 쓰일 내용만 버리기 | 5.6%, 행동이 지지하는 정의로는 약 5.6~13% | 무엇을 "재사용"으로 보나 | — |
| 과거만 보는 단순 규칙 (놓침 < 5%) | 약 3% | — | 하네스 |
| 기계적 하한 (중복·오류·캐시 재작성) | 토큰 0.0008%, **비용 8.92%** | 코드북 v1 | 사용자 / 하네스 |
| 도구 결과 2천/1만 토큰에서 자르기 | 4.4% / 0.3% | 자른 부분은 다시 읽음 | 하네스 |
| 재시도·폴링 고리 모두 없애기 | 약 1.4% | 피할 수 있었음 | 에이전트 |
| AI가 쓴 내용 대신 포인터만 싣기 | 오늘 상한에서는 **약 0 (−4%)**, 비용으로는 손해 | 필요할 때 다시 읽음 | 하네스 / 관례 |
| **맥락 20만이 넘으면 지시 경계에서 새 세션** | **55.2%**. 관측한 다시 읽기와 새 세션의 시동 비용을 매번 물려도 **52~53%** (비용 47~48%) | 재시작마다 필요한 것을 잃지 않음 | **사용자, 오늘 바로** |
| 1시간 넘게 쉬고 돌아왔을 때만 새 세션 | 입력 16%, 비용 20%, 재시작 48번 | 같음 | 사용자, 오늘 바로 |
| 약 39만에서 압축 | 39~44% | 잦은 요약이 필요한 것을 잃지 않음 | 하네스 |
| **압축 상한 15만~20만** | **67~73%** | 같음 | 하네스 (설정 하나) |
| 캐시 수명을 쓸 때마다 고르고 쉴 때 유지 요청 | 총지출 4~6% | 하네스가 고를 수 있음 | 하네스 |
| 읽기를 하위 에이전트에 맡기기 | 주 세션에서 읽을 때보다 1.4~5.1배 쌈 | 같은 읽기가 필요했음 | 에이전트 |

- 지렛대의 효과는 더해지지 않습니다. 같은 맥락에 작용하기 때문입니다.
- 돈으로 보면 효과가 모두 약 5분의 1씩 줄지만 순서는 같습니다. 순서가 바뀌는 것은 기계적 하한 하나입니다. 토큰으로는 0에 가깝고, 돈으로는 약 8%입니다.
- 세션 10개를 다시 뽑아 보면(E4) 상한과 오라클 숫자는 ±1~2%p, 재시작 숫자는 3~5%p 움직입니다.
- 표의 순서는 다시 뽑은 경우의 97% 이상에서 유지됩니다.

## 4. 일의 단위로

- 커밋 하나에 입력 750만 토큰(중앙값)이 들었고, 디스크에 남은 토큰 하나에 약 2,500토큰이 들었습니다.
- 큰 세션은 같은 호출 수에서도 커밋당 1.5배, 남긴 토큰당 2.9배 더 듭니다. 차이는 맥락의 무게입니다(C3).
- 측정한 8주 동안 추세는 없었습니다(D3).

## 5. 그래서

1. **기회의 총량은 튼튼하고, 그것을 나누는 방식은 따로 확인했습니다.** 미래를 안다면 35~56%는 처리하지 않아도 됐습니다.
   - 글자 겹침은 시간에 대칭입니다. 조각이 생기기 전 호출도 생긴 뒤만큼 그 단어를 씁니다. 그래서 겹침은 필요와 주제를 함께 잽니다.
   - 이 효과를 빼면 "다시는 안 쓰인" 몫이 12~45%로 커집니다(E5).
   - 실제 압축 34번 뒤 AI가 다시 읽으러 간 파일로 대조했습니다. 기본 정의는 우연보다 잘 맞혔고(AUC 0.57~0.61), 시간 대칭을 뺀 정의는 우연 수준이었습니다(E8).
   - 그래서 버리기는 5.6~13%일 가능성이 크고, **문제는 버리지 못한 것보다 계속 들고 다닌 것**입니다.
2. **미래를 몰라도 되는 지렛대는 경계를 옮깁니다.** 새 세션을 시작하거나, 일찍 압축하거나, 하위 에이전트에 맡기는 것입니다. 가장 큰 지렛대는 사용자가 오늘 바로 당길 수 있습니다.
3. **요약이 실어야 할 양은 행동으로 보면 작습니다.**
   - 실제 압축 뒤 AI가 다시 가져간 양은 1만~2만 토큰입니다(A5).
   - 새 세션이 자리를 잡는 데는 2만~3만 토큰이 듭니다(B5).
   - 오류율, 걸음 수, 편집 실패 어디에도 눈에 띄는 손상은 없었습니다(A5, D5). 다만 이 지표들은 무딥니다.
   - 경계에서 알 수 있는 어떤 신호로도 더 안전한 재시작 지점을 고를 수 없었습니다(A6). 재시작 규칙은 골라서 안전하게 만들 수 없고, 실험으로 확인할 수밖에 없습니다.
4. **큰 절약은 모두 한 가정 위에 있습니다.** 요약이나 포인터나 하위 에이전트의 답으로 충분하다는 가정입니다. 이것을 뒤집을 수 있는 것은 품질뿐이고, 품질은 기록으로 잴 수 없습니다.
   - 3단계는 테스트가 붙은 실제 작업으로 이것을 확인합니다.
   - 후보 작업 29개(이 저장소의 역사에서 검증)가 `research/phase3/`에 있습니다.
   - 사용자 단위의 이전/이후 실험 사전 등록 초안은 `research/protocol/e1-before-after.md`에 있습니다.
5. **세 가지 공개가 가장 큰 미지수를 없앱니다.** 사용량에서 생각 토큰을 따로 보고하는 것, 이벤트 기록에 최종 출력 토큰을 남기는 것, 압축 호출의 사용량 기록입니다.

## 6. 2단계에 남은 것

- 블라인드 판정: W4·W5·W8 탐지기의 정확도를 재고(W5는 보조 분석까지 사전 등록), 오류만 돌려받은 걸음이 낭비인지 검증인지 가립니다.
- n > 1: 다른 사람들이 `pxt survey run`으로 잰 결과입니다.
